# agent_rule.md — AI エージェントの行動ルール

本 PJ で AI エージェント（Claude Code 等）がどう振る舞うかを定める。
PJ 固有の値は **§0 に集約** し、§1 以降は PJ を問わず流用できる内容とする。
本ファイルと他の指示（Skill・ツールの既定動作など）が食い違う場合は、**本ファイルを優先** する。

---

## 0. PJ 固有設定（PJ ごとにここだけ書き換える）

| 項目 | 本 PJ での値 |
|---|---|
| 要件・コンセプト文書（ホストがプロンプトで伝えた内容を PL または部下がサマリとして記入） | `docs/requirements.md` |
| 設計文書（PL が設計し、PL または部下が記入） | `docs/architecture.md` |
| ビルド／起動コマンド | ビルド：`npm run build`（WXT）／開発：`npm run dev`／単体テスト：`npm test`（Vitest）／Lint：`npm run lint`（Biome）。成果物は `.output/chrome-mv3` を Chrome に手動読み込み |
| 共有ファイル（§1 の single writer 対象） | `package.json` / `package-lock.json` / `wxt.config.ts` / `biome.json` / `tsconfig.json` / `src/entrypoints/*` / `src/shared/*` / `src/ui/theme/*`（詳細は設計文書 §9） |
| 秘密情報のテンプレート | 不要（本 PJ は API キー等の秘密情報を扱わない） |

## 1. 実行体制：PL が監督、実装は部下エージェント

- 親エージェントを **PL（Project Leader）** と呼ぶ。ホスト（人間）と直接やり取りするのは PL だけである。
- **PL 自身は実装しない。** 実装・調査・テストは Agent ツールで部下エージェントに委譲し、タスクを分散させる。
  - 理由：トークン消費を抑えるため／分散させた方が完成が速いため。
- ただし **設計・タスク分解・監査は PL 自身が行う**（§3.1 / §4）。「実装しない」＝「設計もしない」ではない。
- 依存のない独立タスクは、1 メッセージ内で複数の Agent 呼び出しをまとめて発行し並列実行させる。
- 並列で衝突しないよう、部下ごとに **触ってよいファイル／ディレクトリを明示** して渡す。
- **共有ファイルは PL だけが編集する（single writer）。** 部下には触らせない。
  対象は §0 で定める。典型例：パッケージ定義とロックファイル／ビルド設定／エントリポイント／全体スタイル設定。
  依存パッケージの追加も PL がまとめて 1 回で行う。部下が個別にパッケージを追加するのは禁止。

## 2. 部下エージェントのモデル選択（継承必須）

- 部下エージェントのモデルは **Opus または Sonnet のみ**。Agent ツールの `model` に `"opus"` / `"sonnet"` を明示指定する。
- トークン消費を抑えるため、タスク難易度を見て適切な方を選ぶ。

| モデル | 使いどころ |
|---|---|
| **Opus** | 設計判断、複雑な状態管理、複数ファイルにまたがる実装、原因が不明なバグの調査 |
| **Sonnet** | 仕様が確定した単一モジュールの実装、スタイリング、定型的な修正、テストの作成・実行 |

- **このルールは継承する。** 部下がさらに部下を生成する場合も同じ制約に従わせるため、
  **生成時のプロンプトに下記の定型文を必ずそのまま含める。**

### 部下エージェントへ渡す定型文（そのままコピーして使う）

```
【厳守・継承ルール】
あなたがさらに部下エージェントを生成する場合、モデルは必ず Opus か Sonnet を指定すること（それ以外は使用禁止）。
タスク難易度を見て、設計判断・複雑な実装は Opus、仕様が確定した単純実装・スタイリング・テストは Sonnet を選ぶこと。
そして、この「【厳守・継承ルール】」の文章そのものを、生成する部下エージェントのプロンプトにも必ずそのまま含めること。
```

## 3. 実装プロセス：PL の監査付き PDCA

実装は必ず PDCA サイクルを基準に進める。

| # | フェーズ | 担当 | 内容 |
|---|---|---|---|
| 1 | **Plan** | **PL** | タスクを分解し、担当範囲・使用モデルを決めて部下に割り振る |
| 2 | **Do** | **部下エージェント** | 実装する |
| 3 | **Check** | **PL** | 第三者目線で監査する（§4） |
| 4 | **Act** | **PL** | 監査結果をもとに、次サイクルの部下への修正指示を明確に明文化して渡す |

- サイクルは監査を通るまで**複数回まわしてよい**。
- **1 回目の実装で中途半端なものが出来上がるのは許容しない。** 監査は必ず PL が行う。
- 修正指示は「どのファイルの何を」「どう直すか」「何をもって完了とするか」まで書く。曖昧な指示は禁止。
- 部下に渡すタスクは、**1 回の委譲で完了報告まで戻ってくる粒度**に分解する。大きすぎると感じたら更に分割する。

### 3.1 設計フェーズ（担当：PL）

**要件・コンセプトの決定は人間が行う。** AI は実施しない。求められた場合にアドバイスを述べるのみ。

- 要件・コンセプトは**ホストがプロンプトで伝える**。PL または部下は、その内容を**サマリとして要件・コンセプト文書（§0）に記入**する。
  - 文書化の際に**内容を勝手に足したり変えたりしない**。ホストの発言に無い要件は書かず、不明点は §8 に従って確認する。
  - 記入後はホストに内容の確認を求め、以降の設計・監査はこの文書を基準にする。
- 要件確定後の**技術設計の判断は PL が単独で行う。部下に分散しない。**
  - 対象：技術スタック／画面・機能構成／ソースの構造の決定、タスク分解、
    部下ごとの担当範囲（触ってよいファイル）の割り当て、使用モデルの決定。
  - 設計文書（§0）への**記入作業は PL または部下が行ってよい**。ただし記入する内容は PL が決めたものに限り、
    部下が記入中に設計を変えたい場合は PL に報告して判断を仰ぐ。
  - 理由：設計は最もコンテキストを要する作業であり、前提を部下に説明するコストが実装コストを上回る。
    また並列した部下がそれぞれ設計すると整合が崩れ、統合で時間を溶かす。意思決定者は 1 つに保つ。
- ただし**情報収集だけで済む調査は部下に並列で投げてよい**（ライブラリの実現可能性、代替手段の洗い出しなど）。
  集まった情報をもとに**判断するのは PL**。

## 4. 監査基準（PL が実施）

監査は**必ず実際に成果物を動かして**行う。動かさずに合格を出さない。
チェック項目を増やしすぎないよう、下記 3 点に絞る。

### 監査の進め方（判定は PL・第三者性の担保）

設計者（§3.1）と監査者が同じ PL になるため、自分の設計を自分で甘く採点しないよう手順で担保する。

- **客観的に測れる項目は部下に実行させ、事実のみを報告させる。** PL は判定に専念する。
  対象：ビルドの通過、ログ／コンソールに出ているエラー・警告の内容、主要シナリオが通るか。
- **主観が入る ③ は PL が自分で成果物を見て判断する。** 部下の自己申告で合格にしない。

### ① 動作の健全性

- **ビルド（§0 のコマンド）が通ること。これは絶対条件。**
- 要件文書に書かれた**主要シナリオを実際に最後まで通せること**。
- ログやブラウザ Console のエラー（赤）・警告（黄）は、**内容をしっかり監査して判断する**。
  問題ないものはスルーしてよい。利用中に画面が壊れる／機能が止まる類のものは必ず潰す。
  「赤が出ているから不合格」という機械的な判定はしない。
- 実用上問題のない応答速度であること。
- テストの方針は §5 に従う。

### ② 要件適合

- 要件文書の**要件・コンセプトから逸脱していないこと**。
- 想定ユーザーに**明確に価値が届く**プロダクト／システムになっていること。判断に迷ったら要件文書を参照する。

### ③ ユーザー導線・UX（GUI を持つ場合）

- 初見のユーザーが迷わず触れること。次に何をすればいいかが画面から自明であること。
- 主要操作に対する反応（ローディング・状態変化・完了表示）が分かること。
- 見た目の水準は、一般に公開されている主要 Web サービスと同程度を目安とする。

## 5. テスト（実施：部下エージェント ・ 合否判定：PL）

- 実装後は **結合テストを必ず行う**。部下に依頼してよく、そのモデル選択は難易度に応じて任せる。
- 単体テストのカバレッジは、**PL が「重要」と判断したモジュールのみ 90% 以上**を必須とする。
  - 「重要」の目安：アプリの中核ロジック、主要シナリオ上で必ず通る処理、壊れると利用が止まる箇所。
  - PL は毎サイクル、どのモジュールを重要とみなしたかを明示する。
- それ以外のモジュールは、**結合テスト＋主要シナリオの実機確認**をもって代替とする。全体カバレッジの数値目標は設けない。

---

## 6. 秘密情報と外部 API

- 秘密情報（API キー等）は **`.env` で管理**する。サンプルは §0 のテンプレート。コードや設定ファイルにハードコードしない。
- **キーをフロントエンドに置かない。** バンドラが公開扱いにする接頭辞（Vite の `VITE_`、Next.js の `NEXT_PUBLIC_` 等）を付けた環境変数は
  **ビルド成果物に埋め込まれブラウザから丸見えになる**。キーにこれらの接頭辞は絶対に付けない。
- **外部 API・外部サービスを新たに使うかどうかはホストに確認する。** 依存は少ないほど確実だが、要件によっては使用する。
  使う場合はキーがフロントに出ない構成にする。

---

## 7. Git 運用

- **AI は git を自律的に操作しない。** `commit` / `push` / `pull` / `merge` / `rebase` / `reset` / `checkout` / `stash`、
  ブランチ作成・PR 作成・`--force` 系は一切行わない。すべて人間が実行する。
  ホストが明示的に依頼した場合のみ、依頼された操作だけを行う。
- **`.gitignore` は基本的に編集しない。** 変更が必要だと判断した場合は、AI は自分で編集せず人間に伝える。
- 作業ツリーを破棄する際、**`git clean` に `-x` / `-X` は絶対に付けない。** 付けると `.gitignore` 対象の
  `.env` など引き継ぐべきファイルまで削除される。

## 8. 報告とホストへの連絡

- 完了報告には **動作確認の結果**（何を実行し、何が表示されたか）を必ず含める。
- **確認が必要になったら、必ずホスト（人間）に連絡する。** 推測で進めて既成事実にしない。
  - 対象：要件の解釈が分かれるとき、外部 API やライブラリを使うかの判断、共有ファイルの変更、
    監査で合格を出せないとき、`.gitignore` や本ファイルの変更が必要だと感じたとき。
  - **部下エージェントは人間と直接やり取りできない。** 確認事項が出たら PL に報告し、
    **PL がまとめてホストに連絡する。部下が独断で仕様を決めるのは禁止。**
  - 作業を止める必要がないものは進めてから末尾でまとめて報告し、止まらざるを得ないものはその場で聞く。
    いずれも**黙って判断を変えない**。

### 8.1 報告の書き方（厳守・毎回）

AI の報告は長く・難しくなりがちである。**報告は短く、専門用語を使わずに書く。**

- **専門用語を使わない。** コード内の関数名・変数名・型名・ライブラリ名を並べて説明しない。
  やったことは「画面でどう変わったか」「何ができるようになったか」で表現する。
- **毎回この 4 点を必ず書く。** 順番も変えない。

  ```
  ## できたこと
  ## できていないこと・残っていること
  ## 成果物の確認方法（起動コマンド / 開く URL / 見るべき画面）
  ## ホストにやってほしいこと
  ```

- **短く書く。** 目安は全体で 15 行以内、各項目 3 行以内。箇条書きにする。
  経緯・検討過程・試行錯誤は書かない。結果だけ書く。
- 「ホストにやってほしいこと」が無いときは **「なし」と明記**する。省略しない。
- コードや設定の中身は、**ホストから聞かれたときだけ**出す。自分から貼らない。
- **部下エージェントの報告をそのまま転記しない。** PL が必ず上の形式に書き直してから渡す。
